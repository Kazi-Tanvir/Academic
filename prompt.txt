DATE RULE (two cases, decided by the note's type)
`date` is a plain YAML date: YYYY-MM-DD, unquoted, no time. `created` is a
separate property and is always today's date (when the note is written).
Index and reference notes have no `date`.
A) PRACTICE notes (type/practice: everything under a PRACTICE folder, such as
   BRO_CODE, CONCEPT_WISE, LEETCODE, C_BOOK, PYG, IMAGE_EDITOR, BUET, SLIDES):
   `date` = the source file's CREATION date from the file system. Ignore the
   Dates field in TARGET for these.
   - Single-file note: that file's creation date. Multi-file note (`source` is
     a folder and `files` is listed): the EARLIEST creation date among the files.
   - How to read it: on Windows use Python `os.stat(path).st_ctime`, which is
     the creation time there; on other systems use `st_birthtime` if present.
     Do NOT use the modification time. Convert to the machine's local time zone
     so the day is not off by one. Never change a source file's timestamp
     (no `touch`).
   - Sanity check: if 5+ files, or more than half of the practice notes in this
     run, share the exact same creation date, the timestamps were probably
     reset by a clone or copy. Do not use them silently. Report this in Phase 0
     and propose the fallback `git log --diff-filter=A --format=%cs -- <path>`
     (date of the first commit that added the file, take the oldest), then wait
     for my approval.
B) ALL OTHER notes (lecture, lab, assignment, project, archive):
   `date` = the date I give in the TARGET "Dates" field, for that file or its
   folder. Do not read file timestamps and do not guess.
   - If a file has no date from me, list it in Phase 0 and ask. Do not write
     that note until I answer.
   - If I gave one date, it applies to every non-practice note in this run.
If a run mixes both kinds, apply the right rule per note.

RUNNING RULES
- Copy the relevant folder to a TEMP directory outside the repo before
  compiling or running. Never run in place: programs may write or overwrite data
  files.
- C: `gcc -Wall -o <tmp>/prog <file>.c`. Java: check `javac -version`, then
  `javac -d <tmp>/out <files>` and `java -cp <tmp>/out Main`; ignore existing
  bin/*.class files. Never run .exe files. Other languages: use their standard
  compile/run command and say which.
- Interactive programs: pipe small sample input; use the repo's own input files
  when they exist.
- If a program cannot run (GUI, audio, missing compiler or library, needs
  hardware), derive the behaviour from the source and label it
  `> [!note] Traced from the source, not executed.`
- Never paste output you did not obtain or trace.
